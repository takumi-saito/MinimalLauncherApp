# ADR-0001: 軽量 ADR でアーキテクチャ上の意思決定を記録する

**Status**: Accepted
**Date**: 2026-08-03
**Deciders**: @takumi-saito

## Context

このリポジトリには意思決定の記録が無く、判断の理由がコミットメッセージと PR に散っている。
数か月後に「なぜこのライブラリなのか」「なぜこの構成にしたか」を追うには、コミットログを
遡って断片を繋ぎ直すしかない。

コーディングエージェントを使うようになって、この問題の性質が変わった。

- 実装そのものが速くなったぶん、意思決定のコストに対して検討を省く圧力がかかる
- エージェントは既存コードから **何を** やっているかは読めるが、**なぜ** そうしたか・
  **何を採らなかったか** は読めない。結果、一度見送った選択肢を再び提案してくる
- 「実装工数の大きさ」より「変更の不可逆性」が意思決定の重みを決めるようになった

つまり、記録すべきものは減っておらず、むしろ人間とエージェントの両方が読む前提で
必要性が上がっている。

一方でこれは個人開発なので、複数人チーム向けの重い運用（承認者を複数立てる、
Proposed 期間を設けて合議する）はそのまま持ち込むと形骸化する。

## Decision

`docs/adr/` に **軽量 ADR**（Status / Date / Deciders + Context / Decision / Consequences）
を蓄積する。運用ルールは [README.md](README.md) に置く。

判断が分かれた点と、その選択:

**採番はゼロ埋め 4 桁の連番**（`0001-xxx.md`）。
日付ベース（`2026-08-03-xxx.md`）は、複数人が並行して ADR を書くときに採番が衝突しない
利点があるが、個人開発ではその衝突が起きない。連番のほうが「ADR-0002 を参照」と短く
書け、ADR 間の相互リンクが読みやすい。将来コントリビュータが増えて採番が衝突しはじめたら、
日付ベースへの移行を別 ADR で検討する。

**テンプレートは Lightweight ADR 一本に絞る。**
MADR 形式（Decision Drivers / Considered Options / Rationale / Implementation Notes を
個別セクションに持つ）は、個人開発では書く負担のほうが勝つ。採用しなかった選択肢は
Lightweight の Decision セクション内に散文で書けば足りる。

**レビューは PR 上で行い、マージ時点で `Accepted` とする。**
「senior engineer 2 名以上のレビュー」といったチェックは、レビュアーが自分ひとりである
以上ノイズにしかならない。行単位でコメントできる PR という場に載せること自体には
価値があるので、そこは残す。

**書くタイミングは「運用が回りはじめてから」を基本とする。**
PoC 段階で書くと、実際にやってみて変わった部分と食い違い、メンテされない記録になる。

**遡及的な ADR は書かない。**
Hilt の採用や Compose と View システムの併用など ADR 導入以前の決定について、
推測で「当時こう考えたはず」と書くと、事実と願望の区別がつかない記録になる。
該当箇所を触る機会に、そのとき分かっている事実の範囲で書き起こす。

**採用しなかった選択肢: `adr-tools`。**
`brew install adr-tools` で採番・索引生成を自動化できるが、リポジトリ外のツールに
依存すると環境構築の手順が増える。ADR の追加頻度は月に数本程度と見込まれ、
Claude Code の `/adr` スキル（`.claude/skills/adr/`）で採番と索引更新を代行させれば足りる。

## Consequences

**Good**:
決定の理由と却下した選択肢がリポジトリ内に残り、人間とエージェントの両方が同じ根拠を
読める。エージェントに「なぜこの方針か」を毎回説明し直す必要が減り、一度見送った案を
再提案されることも減る。PR に ADR が乗ることで、実装だけでは伝わらない意図が
差分として見える。

**Bad**:
ADR を書く手間が増える。個人開発では「自分は覚えている」ため短期的な効き目を感じにくく、
書かれなくなるリスクが常にある。索引の更新を忘れると ADR が発見されなくなる。
軽量テンプレートは記述の自由度が高いぶん、書き手の気分で粒度がぶれる。

**Mitigations**:
書く対象を「あとで覆すのに数日かかる決定」に絞り、閾値を README に明記して迷いを減らす。
索引の更新は `/adr` スキルの手順に組み込み、手作業から外す。粒度のぶれについては、
`Bad` を必ず埋めることを運用ルールにして最低限の質を担保する（トレードオフを 1 つも
書けない ADR は、検討が足りていないか隠している）。
書かれなくなるリスクは受け入れる。本数をノルマ化するほうが害が大きい。
