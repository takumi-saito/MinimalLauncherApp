# Architecture Decision Records

MinimalLauncherApp のアーキテクチャに関わる意思決定の記録。

「あとから変えるのが高くつく決定」を、決めた理由ごと残す。コードを読めば **何を**
やっているかは分かるが、**なぜ** そうしたか・**何を採らなかったか** はコードに残らない。
そこだけを ADR が引き受ける。

## 書く / 書かない

| 書く | 書かない |
|------|---------|
| ライブラリ・フレームワークの選定 | パッチバージョンの更新 |
| テスト戦略（VRT、カバレッジ方針など） | バグ修正 |
| ディレクトリ構成・レイヤ分割 | 実装の詳細 |
| データモデル・状態管理の方針 | 設定値の変更 |
| CI/CD やリリースフローの方針 | リファクタリング（方針が変わらないもの） |

判断に迷ったら「**あとで覆すのにどれくらいかかるか**」で決める。
数分で戻せるなら書かなくてよい。数日かかるなら書く。

コーディングエージェントで実装そのものは速くなったぶん、意思決定の重みは
「実装工数」から「変更の不可逆性」に移っている。不可逆な決定ほど記録の価値が高い。

## 書くタイミング

**運用が回りはじめてから書く。** 事前検証の段階で書くと、実際にやってみて変わった
部分と食い違い、メンテされないドキュメントになる。

```
調査・PoC  →  本実装  →  しばらく使う  →  ADR にまとめる
```

例外は、実装前に方針を固めないと手戻りが大きいとき（データモデル、外部 API との契約など）。
その場合は `Proposed` で書き、実装後に `Accepted` へ更新する。

## 新しい ADR を追加する

```bash
# Claude Code から
/adr <決めたことの概要>
```

手動でやる場合:

1. `template.md` を `NNNN-title-with-dashes.md` にコピーする
   （`NNNN` は索引の最大値 + 1、ファイル名の slug は ASCII、タイトル本文は日本語で可）
2. 埋める
3. この README の索引に 1 行足す
4. 実装と同じ PR に含めてコミットする

## Status

| Status | 意味 |
|--------|------|
| `Proposed` | 提案中。実装前に方針だけ先に決めた状態 |
| `Accepted` | 採用済み。PR がマージされた時点でこれになる |
| `Deprecated` | もう当てはまらない。置き換え先は特に無い |
| `Superseded` | 別の ADR に置き換えられた。`Superseded by` で参照する |
| `Rejected` | 検討したうえで採用しなかった。**消さずに残す** |

```
Proposed ──→ Accepted ──→ Deprecated
   │                   └─→ Superseded
   └──→ Rejected
```

## 運用ルール

- **Accepted な ADR は書き換えない。** 決定が変わったら新しい ADR を書き、古い方の
  Status を `Superseded` にして相互にリンクする。「当時どう考えていたか」が消えると
  ADR の価値が無くなる。
- **Bad を必ず書く。** トレードオフの無い決定は存在しない。Good しか書かれていない
  ADR は、検討していないか、都合の悪い点を隠している。
- **1〜2 ページに収める。** 長い ADR は読まれない。詳細な手順は別ドキュメント
  （例: [docs/vrt.md](../vrt.md)）に切り出し、ADR からリンクする。
- **Rejected も残す。** 「一度検討して見送った」情報は、同じ検討を繰り返さないために効く。

## 既存の決定について

このリポジトリには ADR 導入以前からの決定（Hilt の採用、Compose と View システムの併用、
ViewPager2 での画面切り替えなど）がある。これらは遡って書き起こしていない。
推測で「当時こう考えたはず」と書くと、事実と願望の区別がつかない記録になるため。

該当箇所を触る機会に、そのとき分かっている事実の範囲で書き起こす。
